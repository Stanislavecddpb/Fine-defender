# ТЗ — Аддендум: Личный кабинет селлера (мультитенантность, авторизация)

> Дополнение к базовому ТЗ Fine Defender. Описывает превращение MVP-дашборда
> (раздел 8 базового ТЗ) в полноценный личный кабинет, готовый к работе с
> реальными клиентами. Версия документа: 1.0.

## 1. Зачем

В MVP дашборд показывал данные первого селлера без авторизации, а `seller_id`
передавался query-параметром — это годилось для демо, но **непригодно для
реальных клиентов**: нет входа, нет разделения данных между арендаторами, любой
запрос мог обратиться к чужому `seller_id`.

Аддендум закрывает это: вход, самостоятельная регистрация, ввод WB-токена и
строгая изоляция данных по тенанту.

## 2. Скоуп

### В скоупе
- **Регистрация** селлера: email + пароль + название компании + WB-токен.
- **Вход / выход** по email+паролю (сессия в подписанной cookie).
- **Изоляция по тенанту:** все данные (`/api/*`) принадлежат селлеру из сессии;
  `seller_id` из запроса **не принимается**.
- **Защита от IDOR:** доступ к штрафу/черновику только если он принадлежит
  текущему селлеру (иначе 404).
- **Управление WB-токеном из кабинета:** добавить/заменить токен (шифруется).
- **Запуск проверки по кнопке:** селлер инициирует выгрузку+классификацию своего
  кабинета и сразу видит результат (не дожидаясь фонового воркера).
- **Кабинет-UI:** экраны «Вход / Регистрация», «Ввести токен», «Дашборд штрафов».

### Вне скоупа (намеренно, на этом этапе)
- Восстановление пароля по email, подтверждение email, 2FA.
- Роли и несколько пользователей на одного селлера (1 селлер = 1 логин).
- OAuth/SSO, биллинг, тарифы.
- Платёжная интеграция success fee.
- Роль оператора/админа в UI (оператор работает через БД/скрипты, как в MVP).

## 3. Модель данных (дельта)

Таблица `sellers` дополняется:

```sql
ALTER TABLE sellers ADD COLUMN email         TEXT UNIQUE;   -- логин
ALTER TABLE sellers ADD COLUMN password_hash TEXT;          -- pbkdf2_sha256$...
```

- `email` — уникальный логин. Nullable для совместимости с селлерами, заведёнными
  оператором без логина.
- `password_hash` — формат `pbkdf2_sha256$<iterations>$<salt_hex>$<hash_hex>`.
  Соль на пользователя, ≥ 600 000 итераций (OWASP). **Пароль в открытом виде
  нигде не хранится и не логируется.**
- WB-токен по-прежнему в `wb_token_enc` (envelope encryption), теперь может быть
  пустым до ввода в кабинете.

## 4. Аутентификация и сессии

- Сессия — **подписанная cookie** (Starlette `SessionMiddleware`, `HttpOnly`),
  содержит только `seller_id`. Секрет подписи — `SESSION_SECRET` (env; в проде
  обязателен и не дефолтный).
- Пароли — `pbkdf2_hmac('sha256', ...)` (stdlib), без хранения plaintext.
- Эндпоинты аутентификации:

| Метод | Путь | Назначение |
|------|------|-----------|
| POST | `/auth/register` | регистрация: email, пароль, компания, (опц.) токен → вход |
| POST | `/auth/login` | вход по email+паролю |
| POST | `/auth/logout` | выход (очистка сессии) |
| GET | `/auth/me` | текущий селлер: id, name, email, есть ли токен, scopes |

## 5. API кабинета (всё — в контексте текущего селлера)

`seller_id` берётся **из сессии**, не из запроса. Каждый защищённый эндпоинт
требует валидной сессии (иначе 401).

| Метод | Путь | Назначение |
|------|------|-----------|
| GET | `/api/fines?status=&category=` | штрафы текущего селлера |
| GET | `/api/fines/{id}` | карточка штрафа (только свой — иначе 404) |
| GET | `/api/summary` | сводка «под возврат / отбито ₽» |
| POST | `/api/fines/{id}/draft` | сгенерировать черновик претензии (только свой) |
| POST | `/api/fines/{id}/events` | действие: статус, recovered_amount, заметка |
| POST | `/api/token` | задать/обновить WB-токен (шифруется) |
| POST | `/api/ingest/run` | запустить выгрузку+классификацию своего кабинета сейчас |

## 6. Сценарии (UX)

**Регистрация нового клиента:**
1. Открывает кабинет → экран «Регистрация».
2. Вводит email, пароль, название компании, WB-токен (read-only «Финансы»).
3. Система создаёт тенанта, шифрует токен, логинит.
4. Жмёт «Запустить проверку» → видит найденные штрафы и дедлайны.

**Возврат клиента:** вход по email+паролю → сразу дашборд со своими штрафами.

**Нет/протух токен:** кабинет показывает экран ввода токена; после сохранения —
кнопка «Запустить проверку».

## 7. Безопасность (требования)

- **Изоляция тенантов** — основное требование. `seller_id` только из сессии;
  любой доступ к чужому объекту → 404 (не 403, чтобы не раскрывать существование).
- Пароли хэшируются (pbkdf2, соль, высокие итерации); токен шифруется; ни то ни
  другое не пишется в логи.
- Сессионная cookie — `HttpOnly`, подписана секретом; в проде — `Secure` (HTTPS).
- Регистрация/вход — единый ответ при неверных кредах (не раскрываем, существует
  ли email).

## 8. Совместимость и миграция

- Миграция `002_auth.sql` идемпотентна (`ADD COLUMN IF NOT EXISTS`).
- Селлеры без `email`/`password_hash` (заведённые оператором) продолжают работать
  для фонового воркера; войти в кабинет они не могут, пока им не зададут логин.
- Демо-режим (`APP_BACKEND=memory`/`seed_demo`) заводит демо-селлера **с логином**
  (печатается при засеве), чтобы кабинет можно было открыть без регистрации.

## 9. Критерии готовности

- [ ] Незалогиненный запрос к `/api/*` → 401.
- [ ] Селлер A не видит данные селлера B (список пуст, прямой доступ по id → 404).
- [ ] Регистрация создаёт тенанта и логинит; повторный email → ошибка.
- [ ] Ввод токена в кабинете + «Запустить проверку» наполняет дашборд.
- [ ] Пароль и токен отсутствуют в логах и ответах API.
- [ ] Все автотесты (вкл. изоляцию тенантов) зелёные; интеграция с Postgres — тоже.
